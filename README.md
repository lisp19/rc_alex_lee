# API 通知投递系统

> 考核方请参考 [answer.md](answer.md)，其中包含对需求的理解和原始问题的回答。本文介绍项目架构。

面向外部 HTTP(S) 接口的通用通知服务，提供持久化受理、异步与 Proxy 投递、结果判定、有界重试和状态查询。系统不感知供应商业务逻辑，可靠性责任从通知成功持久化开始。

## 整体架构

![通知服务与数据存储、调度、配额及配置依赖](docs/images/architecture.png)

| 组件 | 职责 |
|---|---|
| 通知服务 | API 受理、HTTP 投递、Outbox 发布和故障恢复；各角色可独立部署与扩缩容 |
| MariaDB | 保存通知、尝试记录、Outbox 和配置版本，是任务状态的唯一事实源 |
| RabbitMQ | 使用持久化 Quorum Queue、发布确认和手动 ACK 提供至少一次调度，通过 TTL 与 DLX 承载延迟重试 |
| Redis | 提供共享配额与辅助锁，不承担任务持久化或最终状态判断 |

业务数据与管理配置逻辑隔离，运行服务对管理库只读。Target 描述供应商地址、认证、幂等能力和响应规则；Client 定义调用方身份、允许访问的 Target 及人工重试权限。

## 可靠性

- **事务受理**：通知与 Outbox 同事务保存，避免任务已受理但调度事件未记录。
- **执行隔离**：数据库 generation 和租约约束执行权与结果写回；HTTP 调用不占用数据库事务锁。
- **故障恢复**：过期租约、未完成发布及缺失调度均可从数据库恢复，进程重启不依赖本地状态。
- **有界重试**：次数、期限和 Retry-After 共同约束自动重试；人工重试保留原任务及对外幂等键。
- **重复控制**：上游提交通过幂等键去重；下游支持 Header、Query 或 JSON 正文注入稳定幂等键，不确定结果是否可重试由 Target 显式定义。

Proxy 同样先持久化，再等待第一次投递结果。成功默认指符合规则的 HTTP 响应，不保证供应商业务完成；系统不承诺 Exactly-once 或顺序投递。

## 配置与安全

管理配置以不可变版本快照加载，刷新失败保留有效配置。重试、Hook 和幂等行为使用任务固化版本；身份授权、Target 禁用、地址限制和认证使用最新有效配置。

API 使用 JWT 鉴权并限制 Client 的访问范围。目标地址由配置控制，校验 DNS 解析后的 IP，禁止自动重定向；Secret 通过引用注入，日志与响应摘要脱敏。CEL Hook 仅在受限资源预算内解析响应，不能执行任意代码或访问外部资源。

## 部署形态

应用进程无状态，可在容器平台水平扩容，也可将 API 与后台投递角色分开部署。生产环境由网关提供 HTTPS 入口，业务库、管理库、RabbitMQ 和 Redis 使用独立账户及受管依赖；数据库备份与中间件高可用由部署平台保障。

共享配额限制调用方和 Target 的速率及并发。Redis 故障时可按策略拒绝请求或降级到进程并发限制，任务正确性仍由数据库保证。健康检查区分进程存活与服务就绪，结构化日志提供投递、重试、积压和配置状态，便于接入监控平台。
