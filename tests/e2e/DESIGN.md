# 运行时端到端测试设计与正交分组

## 1. 测试边界与发布门槛

在既有 20 项基础冒烟、3 项恢复冒烟上扩展为 **51 个可执行 E2E case**：

| 级别 | 定义 | 数量 | 门槛 |
|---|---|---:|---|
| P0 | 数据受理/投递正确性、身份隔离、持久化/恢复的核心链路 | 12 | 任一失败阻断交付 |
| P1 | 配置版本、重试/Hook、幂等注入、Quota 和 MQ 补偿等主要功能及交互 | 21（12 专项 + L9 的 9 行） | 交付前修复；不以降级断言代替修复 |
| P2 | 边界、响应保护、热更新、运行角色、分页及生命周期扩展 | 18（10 专项 + L8 的 8 行） | 记录并修复实际缺陷；环境问题单独标记 |

测试只调用真实 HTTP/API、运行管理 CLI、真实 MariaDB/Redis/RabbitMQ、真实 Docker 实例。供应商模拟器本身是独立运行的 HTTP 服务，保留实际收到的请求观测。**不导入应用内部包，不使用单元测试框架，不替换 Repository/Clock/Transport，也不执行 `go test`。** 构建供应商辅助程序不是单元测试。

用例使用正常业务 API 创建任务；SQL 主要用于只读核验。在 P1-12 唯一的 SQL 状态注入中，仅修改该用例的 Outbox 发布租约以模拟 Publisher 崩溃，不修改 Notification 状态/时间/generation，不直接写 delivered，不压缩真实租约和重试时间。P1-11 从真实 TTL Queue 移除本用例的消息模拟 Broker 消息丢失，等待真实 60 秒 Reconciler 宽限期。

## 2. 统一前置、步骤与观察依据

统一前置：上一阶段本地双实例健康；`.env` 和 `configs/secrets/` 已初始化；端口 18091 可用；本项目独占验收窗口，无其他生产任务正在投递。测试开始用文件锁串行化所有 E2E 进程。

统一准备：生成唯一 run ID；编译并启动真实供应商模拟器；从当前管理文档生成专用 Client/Target/Policy；通过运行中的 `notify-admin` 提交；等待两个实例加载相同 revision。临时 Secret 挂载和 Compose override 在运行时生成，测试结束恢复原始进程配置和活动管理配置内容（使用新的 global revision），不回写历史 revision。

三类观察证据交叉核验：

1. API：HTTP 状态码、标准错误、Notification 状态、generation、Attempt 序号与结果；从另一实例查询。
2. 数据事实：业务表、唯一逻辑任务、NULL report、Outbox、权限拒绝、配置 revision。
3. 外部执行：供应商实际调用次数、时间、收到的幂等键、正文 SHA-256、并发数、Secret 摘要；MQ 拓扑/Consumer/DLQ；实例日志和健康状态。

测试通过不只看 HTTP 202。每个受理的正向任务必须收敛为预期终态，失败/限流/隔离用例必须证明不存在不应发生的外部调用或重复任务。

## 3. 正交组 O1：L9(3⁴)，P1

因素与水平：

| 列 | 因素 | 0 | 1 | 2 |
|---|---|---|---|---|
| A | 供应商结果 | 200 | 503 后 200 | 400 |
| B | 提交模式 | async | proxy | batch（async） |
| C | 幂等注入 | Header | Query | JSON Pointer（嵌套数组） |
| D | 入口 | 实例 A | 实例 B | A/B 同 Key 并发 |

| case | A | B | C | D |
|---|---:|---:|---:|---:|
| O1-01 | 0 | 0 | 0 | 0 |
| O1-02 | 0 | 1 | 1 | 1 |
| O1-03 | 0 | 2 | 2 | 2 |
| O1-04 | 1 | 0 | 1 | 2 |
| O1-05 | 1 | 1 | 2 | 0 |
| O1-06 | 1 | 2 | 0 | 1 |
| O1-07 | 2 | 0 | 2 | 1 |
| O1-08 | 2 | 1 | 0 | 2 |
| O1-09 | 2 | 2 | 1 | 0 |

每行步骤：按四列生成业务请求 → 对应实例/模式受理 → 等待真实投递/TTL 重试 → 双实例查询 → 检查供应商观测。预期：200 一次 delivered；503→200 两次 delivered；400 一次 failed；并发入口仍只有一个逻辑 Notification，所有尝试复用同一幂等键。

覆盖证明：任意两列的 3×3 水平组合均出现且恰好一次，共 **6 个列对 × 9 个组合 = 54 个二因素组合**。这是二因素正交覆盖，不声称覆盖全部 3⁴=81 个组合或所有高阶交互。

## 4. 正交组 O2：L8(2⁴)，P2

| 列 | 因素 | 0 | 1 |
|---|---|---|---|
| A | 模式 | async | proxy |
| B | Method | POST | PUT |
| C | 编码 | UTF-8 | base64（相同解码字节） |
| D | 入口 | 实例 A | 实例 B |

使用三个独立二进制因素 A/B/C，第四列 D=A XOR B XOR C：

| case | A | B | C | D |
|---|---:|---:|---:|---:|
| O2-01 | 0 | 0 | 0 | 0 |
| O2-02 | 0 | 0 | 1 | 1 |
| O2-03 | 0 | 1 | 0 | 1 |
| O2-04 | 0 | 1 | 1 | 0 |
| O2-05 | 1 | 0 | 0 | 1 |
| O2-06 | 1 | 0 | 1 | 0 |
| O2-07 | 1 | 1 | 0 | 0 |
| O2-08 | 1 | 1 | 1 | 1 |

每行步骤：按模式/方法/编码/入口受理 → 等待终态 → 核对外部字节摘要。预期：一次 delivered，供应商实际收到的正文 SHA-256 与编码前字节一致。

任意列对的四种组合各出现两次，共 **6×4=24 个二因素组合**。此组全部使用合法身份和请求，避免 401/403 等先行失败掩盖编码/Method/入口的交互。非法身份与输入使用专项负向组。

`run.py --list` 检查矩阵频数并输出覆盖证明。这是用例设计完整性校验，不是应用单元测试。实际每一行都将运行真实端到端流程。

## 5. P0 专项用例

以下全部继承第 2 节前置，详细请求值在 `cases.py` 对应同名 ID 中。

| ID | 场景与执行步骤 | 预期与判据 |
|---|---|---|
| P0-01 | 检查双实例、四业务表、MQ 拓扑与 Consumer；用受限账户尝试越权 SQL | 两实例身份不同且 Ready；9 个 Quorum Queue、2 个 Manual ACK Consumer；越权被拒绝 |
| P0-02 | 正常受理，在另一实例查询，检查无 Hook 的 Attempt | 一次 delivered；NULL report 不导致 503；外部只收到一次；响应不含请求快照 |
| P0-03 | 8 个跨实例同 Key 并发；修改正文再次使用该 Key | 一个 ID/一次执行；不同内容 409 |
| P0-04 | 缺失/过期 exp、未来 nbf、错误 iss/aud/sub/client/算法；跨 Client 查询及 binding 撤销 | 401/403/404 和关联 request_id 正确；无越权执行 |
| P0-05 | Batch 合法项、非法 Target、错误 item 类型混合；另建批次重放合法项 | 项目独立；只受理合法项；原任务/原 batch_id 保留；不重复执行 |
| P0-06 | 供应商依次配置 200/299/400/404/408/429/500/503 | 2xx 成功，普通 4xx 终止，408/429/5xx 重试；实际 Attempt 数一致 |
| P0-07 | Proxy 分别遇到成功、终止、可重试结果 | 持久化后执行；状态/次数与 async 一致；竞争时允许 202 后查询终态 |
| P0-08 | 停 MQ → 检查 Not Ready → 提交 → 恢复 MQ | pending/0 attempts 持久受理；重连后成功，不丢任务 |
| P0-09 | 停 MariaDB → 提交/检查 Health → 恢复 DB → 相同 Key 重提 | DB 不可用不返回虚假受理；原 Key 无记录；恢复后成功 |
| P0-10 | 停 Redis，使用 fail-open 提交，再启动 Redis | Ready 且 degraded；DB lease-only 完成；恢复健康 |
| P0-11 | 供应商慢响应期间定位 Worker，kill -9 后重启 | 真实 Lease 到期，旧 Attempt unknown，新 generation 成功，累计两次 |
| P0-12 | 先制造 failed；4 个跨实例人工重试并发；成功后再次 retry | 一次 202、三次 409；仅一个新周期，ID/key 保持；delivered 不可重试 |

## 6. P1 专项用例

| ID | 场景与执行步骤 | 预期与判据 |
|---|---|---|
| P1-01 | CEL 覆盖 503 为 success、业务码 retry/fail、report 沿用 HTTP 结果 | 动作/Attempt/report 与契约一致 |
| P1-02 | 固定序列耗尽、deadline、不允许重试、unknown 是否许可 uncertain retry | 有界终止；明确许可的网络不确定错误才能重试 |
| P1-03 | Retry-After 秒数、HTTP 日期、非法值和极大值 | 合法/非法回退均不早于 Bucket；超范围终止，不无界等待 |
| P1-04 | Header、Query、嵌套数组 JSON Pointer 各经历一次自动重试 | 每次外部注入 key 与逻辑 key 一致 |
| P1-05 | method/Header 大小写和 UTF-8/base64 等价字节跨实例重放 | 请求 hash 规范化，返回原 ID，不再次执行 |
| P1-06 | Redis 同一时间窗跨实例入口限额；三项出口限额 | 入口一次受理一次 429；出口分窗执行且等待额度不消耗 Attempt |
| P1-07 | async/proxy 混合并发请求配置并发=1的 Target | 供应商实际观测 active 最大为 1，所有任务最终成功 |
| P1-08 | 激活 closed policy 后停止 Redis；入口拒绝、已受理出口等待；恢复 | 入口 503；出口 pending/0 attempts 无外部请求；恢复后成功 |
| P1-09 | 在已安排重试后禁用当前 Target，同时提交新任务 | 新任务拒绝；历史任务不再调用供应商，进入 failed |
| P1-10 | 旧任务重试前更换 Hook；分别查询旧任务和提交新任务 | 旧任务固化版本成功，新任务使用新 Hook failed |
| P1-11 | 注入 stale generation、非法内部消息；移除本用例已确认 TTL 消息 | stale 不执行；非法消息进 DLQ；真实 Reconciler 推进 generation 补发丢失消息 |
| P1-12 | MQ 故障期间将本用例 Outbox 发布 token/lease 设为崩溃状态 | lease 自然过期后回收；MQ 恢复后一次成功 |

## 8. 分组调度、隔离与失败处理

- 顺序：P0 → P1 专项/O1 → P2 专项/O2。正交表减少组合，不代替专项故障/边界覆盖。
- `foundation/admission/delivery/security/state`：稳定依赖组；case 内可有受控跨实例并发。
- `fault/mq/outbox/config/roles/lifecycle`：独占共享环境，禁止 case 之间并行。真实等待 5s Bucket、60s Lease/Reconciler。
- `quota`：独占当前环境，使用专用 Client/Target/Policy，选择 Redis 固定窗口中部运行以避免合法跨窗误报。
- 不将“重试测试直到偶然成功”作为通过标准；业务错误与测试工具错误分别记录，失败保留原始证据。修复后按 ID 重新执行受影响 case 和相关链路回归。
- 全部运行产物进入 `.runtime/e2e/<run-id>/`；配置/Secret、provider 二进制、临时 Compose、日志、任务 ID、results 都不提交。
- 仅 `tests/e2e/` 中用例文档、测试执行代码和供应商辅助源码受 Git 跟踪。生产代码修复按用户本轮约束保持为单独工作树修改，汇报文件与差异，不混入用例提交。

## 9. 明确未覆盖的维度

本组不是生产容量/长稳测试，不覆盖 Kubernetes 调度、多副本中间件脑裂/灾备、所有 TLS/证书/JWKS 轮换实现或全组合高阶交互。供应商 HTTP 服务在真实网络上模拟响应，不声称真实外部供应商业务成功。上述限制不改变 51 个具体 case 的断言。
